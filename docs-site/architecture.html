Specification — production architecture

Mercito — architecture

How the pieces connect: DNS, the server, Coolify, the database, Cloudflare R2, the app and the docs site.

The full picture

Walking through each connection

1. Domain → server

Loopia holds the DNS for mercito.org: the root (@), www, docs and about each have an A record pointing at the Hetzner VPS's public IP. That is Loopia's entire role — it is not involved once the browser has the IP.

2. Request path

Every request for mercito.org lands on Coolify's built-in proxy (Traefik), which terminates SSL (a Let's Encrypt certificate, auto-renewed) and forwards it to the app container's internal port 3000. There is no separate Nginx — Coolify's proxy is the only thing in that role, by design (see STACK.md).

3. What the app talks to

  • Postgres, for all metadata (users, media files, items, tags, payout splits) — via Prisma, using the internal connection string set as the DATABASE_URL environment variable in Coolify. The database container has no public access; only other containers on the same Docker network can reach it.
  • Cloudflare R2, for the actual audio/video files — but only to sign URLs and check that uploads arrived. The file bytes themselves never pass through the app (see 4).

4. Media storage — Cloudflare R2, EU jurisdiction

Files live in the R2 bucket mercito-media, created under EU jurisdiction so the data stays in the EU (GDPR). Because of that, the bucket is only reachable through the .eu. endpoint (<account-id>.eu.r2.cloudflarestorage.com). The bucket is private — no public URL, no custom domain. Credentials live only in Coolify's environment variables. Everything goes through lib/storage.ts, switched on by STORAGE_DRIVER=r2.

  • Playing — when a page renders, the app creates a presigned GET URL for the file, valid for one hour, and puts it straight into the <audio>/<video> tag. The browser streams from R2, including range requests for seeking.
  • Uploading — the upload form first asks /api/upload/presign for a storage key and a presigned PUT URL, then sends the file directly to R2 with a progress readout, so large files never pass through the app's memory. Only after that does it post the title, tags, credits and the key to /api/upload, which checks the object really exists in R2 before creating the database rows. The bucket's CORS policy allows those PUTs from mercito.org, www.mercito.org and localhost:3000.
  • Keys — the object key is the same string as MediaFile.filePath (e.g. /media/sound/1794584804613-episode.wav), so switching storage drivers never needs database changes.
  • Local dev — without STORAGE_DRIVER, files go to public/media/ (git-ignored) and are served by /api/media/:id/file.

5. Deploy path

Pushing to main on GitHub does not deploy by itself — a Redeploy in Coolify pulls the latest commit, builds a fresh image with Railpack (Coolify's builder) and swaps the running container for the new one. Railpack skips npm install scripts, so the build script runs prisma generate && next build explicitly rather than relying on a postinstall hook.

6. Docs site

A second Coolify app in the same project builds docs-site/ — a tiny dependency-free Node server — and serves it on docs.mercito.org. The same container also answers about.mercito.org, where / opens directly on the Declaration as a public "what is Mercito" page. No login on either.

Manual operations (not yet automated)

  • Deploying — push to main, then Redeploy the app in Coolify.
  • Schema changes — migrations don't run on deploy. After deploying a change to prisma/schema.prisma, run npx prisma migrate deploy inside the app container (Coolify → app → Terminal).
  • New media — uploaded through /upload on the site; no server-side step. The seed script (prisma/seed.ts) is for local dev only, where it reads public/media/.
